SPEC-00

Common Interfaces and Package

cmd / sts / data-beat channels, sgdma_pkg types, AXI4 / AXI4-Lite / AXI-Stream subsets

Verification engineer handout
Document: SPEC-00Revision: 1.0Date: 13 Nov 2026

1What this document describes

The SG-DMA is built from six blocks that talk to each other through three kinds of simple internal channels:

  • a command channel (cmd): "please move N bytes starting at address A",
  • a status channel (sts): "done, I moved M bytes, error yes/no",
  • a data-beat channel (din_* / dout_*): the data itself, 4 bytes per clock beat.

All three use the same valid/ready handshake. This document defines the handshake, the payload types in sgdma_pkg, and the subsets of AXI4, AXI4-Lite and AXI-Stream used on the external ports. Every block spec (SPEC-04 ... SPEC-09) refers back to these rules, and so do the interfaces you write for your testbench.

1.1Example walkthrough: one command and its status

  1. The descriptor engine puts cmd = {addr: 0x0000_2000, len_bytes: 10, inc_addr: 1, desc_id: 0, ...} on the command channel and sets cmd_valid = 1.
  2. The read engine is idle, so it has cmd_ready = 1. On the next rising clock edge both are 1: the command is transferred (one handshake = one command). The descriptor engine drops cmd_valid.
  3. The read engine moves the data: 10 bytes = 3 beats on its dout_* data channel (keep = 1111, 1111, 0011; last = 1 on the third beat).
  4. The read engine then raises sts_valid with sts = {desc_id: 0, err: 0, eop_seen: 0, bytes_done: 10} and holds it until the descriptor engine answers sts_ready = 1.
  5. Only now does the read engine raise cmd_ready again for the next command.

3The valid/ready handshake

Every internal channel has a sender (drives valid and the payload) and a receiver (drives ready). Both are synchronous to the rising edge of clk.

Table 0-4: Handshake rules (all internal channels)
Spec IDRequirement (the design SHALL ...)
IF-HS-001A transfer ("handshake") takes place on a rising edge of clk at which valid = 1 and ready = 1. One handshake moves exactly one item (one command, one status or one data beat).
IF-HS-002Once the sender has set valid = 1, it keeps valid = 1 and keeps the payload stable until the handshake. It may not withdraw or change the item.
IF-HS-003The sender does not wait for ready before raising valid.
IF-HS-004The receiver may set ready before, together with, or after valid, and may change ready in any cycle. Holding ready = 0 is called back-pressure; it may last any number of cycles.
IF-HS-005The payload has no meaning while valid = 0; checkers ignore it.
IF-HS-006After a handshake the sender may present the next item in the very next cycle (back-to-back transfers).
IF-RST-001Reset rst_n is active low and asynchronous. While rst_n = 0 every sender drives valid = 0. This applies to the DUT and to every testbench driver.

4Command channel

Table 0-5: Command channel signals
SignalWidthDirectionDescription

cmd_valid1sender → receivercommand present

Table 0-6: Command channel rules
Spec IDRequirement (the design SHALL ...)
IF-CMD-001An engine sets cmd_ready = 1 only while it is idle. One handshake transfers one command.
IF-CMD-002Every accepted command produces exactly one status on the status channel, with sts.desc_id = cmd.desc_id.
IF-CMD-003An engine processes one command at a time: it accepts the next command only after the status of the current command has been transferred.
IF-CMD-004A command with len_bytes = 0 is illegal. The engine moves no data, makes no bus access and returns a status with err = 1 and bytes_done = 0. Each engine spec lists further illegal commands.

Table 0-10: Data-beat channel rules
Spec IDRequirement (the design SHALL ...)
IF-DAT-001Byte order is little-endian: lane 0 (data[7:0]) carries the byte at the lowest address, lane 3 (data[31:24]) the byte at the highest address of the beat.
IF-DAT-002A beat carries 1 to 4 bytes. When a transfer length is not a multiple of 4, the final beat uses the low lanes only: keep = 0001, 0011 or 0111 (see keep_mask()).
IF-DAT-003last = 1 marks the final beat. Each block spec says exactly when its output sets last and how it reacts to last on its input.
IF-DAT-004Beats are transferred in address order; no beat is duplicated or dropped.

7External bus subsets

7.1AXI4 (memory-mapped masters of sgdma_desc, sgdma_mm_rd, sgdma_mm_wr)

Spec IDRequirement (the design SHALL ...)
IF-AXI-001Every burst uses 4-byte beats: AxSIZE = 3'b010.
IF-AXI-002Only INCR (AxBURST = 2'b01) and FIXED (2'b00) bursts are used; WRAP is never used.
IF-AXI-003A burst has at most 16 beats: AxLEN ≤ 15. The number of beats is AxLEN + 1.
IF-AXI-004An INCR burst never crosses a 4 KB address boundary: the first and the last byte of the burst have the same addr[31:12].
IF-AXI-005A master has at most one burst outstanding per direction: the next AR is issued only after the RLAST beat of the previous read burst; the next AW only after the B response of the previous write burst.
IF-AXI-006A write burst has exactly AWLEN + 1 W beats; WLAST = 1 on the last one and only on the last one. W beats of a burst follow (or coincide with) its AW.
IF-AXI-007Responses are OKAY (2'b00) or SLVERR (2'b10). Anything other than OKAY is an error.
IF-AXI-008All AXI valid/ready pairs follow IF-HS-001 ... IF-HS-004 (AXI uses the same handshake).

Not present on these ports: ID, USER, QOS, CACHE, LOCK, PROT, REGION signals.

7.2AXI4-Lite (CSR slave port of sgdma_csr)

Single-beat 32-bit reads and writes, five channels (AW, W, B, AR, R), byte strobes on W, responses OKAY or SLVERR. The CSR decodes the low 8 address bits. Details in SPEC-04.

7.3AXI-Stream (sgdma_axis_src master port, sgdma_axis_snk slave port)

Spec IDRequirement (the design SHALL ...)
IF-AXS-001A stream beat is transferred on a rising edge with TVALID = 1 and TREADY = 1. Once TVALID = 1, the master keeps TVALID and TDATA / TKEEP / TLAST / TUSER stable until the handshake.
IF-AXS-002TKEEP[i] = 1: byte lane i is valid (IF-DAT-001 lane order). TLAST = 1: final beat of a packet.
IF-AXS-003TUSER (master port of sgdma_axis_src only) is 1 on the first beat of a packet (start-of-packet, SOP) and 0 on all other beats.

8Building a testbench interface from this spec

Each block spec lists its simple valid/ready ports. For each group of ports (one channel, or one set of plain control wires) you write one SystemVerilog interface. A good interface contains:

  1. the clock and reset as ports: interface my_cmd_if (input logic clk, input logic rst_n);
  2. one signal per DUT port of the group, with the same width/type (sgdma_cmd_t cmd; needs import sgdma_pkg::*;),
  3. clocking blocks: one for a driver on the sender side, one for a driver on the receiver side (if you need it), one for monitors (inputs only),
  4. optionally: SystemVerilog assertions for IF-HS-002 (payload stable while waiting) and IF-RST-001.
interface toy_chan_if (input logic clk, input logic rst_n);   // made-up example, not an SG-DMA port
  import sgdma_pkg::*;
  logic [7:0] payload;
  logic       valid;
  logic       ready;

  clocking snd_cb @(posedge clk);          // a driver that SENDS items
    default input #1step output #1;
    output payload, valid;
    input  ready;
  endclocking

  clocking rcv_cb @(posedge clk);          // a driver that RECEIVES items (drives ready)
    default input #1step output #1;
    input  payload, valid;
    output ready;
  endclocking

  clocking mon_cb @(posedge clk);          // monitors only sample
    default input #1step;
    input payload, valid, ready;
  endclocking

  // IF-HS-002 style check: payload stable while valid waits for ready
  property p_stable;
    @(posedge clk) disable iff (!rst_n) (valid && !ready) |=> (valid && $stable(payload));
  endproperty
  a_stable: assert property (p_stable) else $error("payload changed while waiting for ready");
endinterface
The table in your tb_connections.html lists, for every DUT port, a suggested interface signal name, the direction and the suggested config_db name.
