2Scope

In scope: Stand-alone, block-level verification of sgdma_mm_rd (J3) against SPEC-06 and the applicable protocol/interface rules in SPEC-00. Verification covers command acceptance and illegal-command handling; AXI4 read address/burst generation (ARSIZE/ARLEN/ARBURST, INCR/FIXED behavior, 16-beat and 4 KB burst splitting, and one-outstanding burst sequencing); read data forwarding on dout (data/keep/last/valid/ready) including back-pressure; status generation, fields, and ordering (sts, desc_id, eop_seen, err, bytes_done); AXI read-error (SLVERR) behavior; reset behavior; and handshake/stability rules on the verified interfaces, as planned in Features F01–F21.

Out of scope: Integration of sgdma_mm_rd into sgdma_top or with other SG-DMA blocks; descriptor fetch, CSR programming, and system/software-level flows; AXI write-channel functionality; formal verification; and code-coverage closure or performance/latency targets beyond the functional and protocol behavior required by the specification.

Environment and assumptions: Verification uses the provided J3 harness/testbench infrastructure (tb_top, clock/reset generation, rst_if, axi4_if, sgdma_axi_mem with axi_mem_bd_if backdoor, and passive axi4_agent) as delivered, with user-implemented UVM components (cmd/dout/sts interfaces and agents, sequences/tests, reference model, scoreboard/checkers, and functional coverage) connected per the TB connections guide. Memory initialization and error injection are performed through the memory-model backdoor; AXI ready/response timing and stall behavior are determined by the provided memory model and its configured knobs.

References: SPEC-00 (Common Interfaces), SPEC-01 (descriptor/CSR context, as applicable), SPEC-03 (Memory Model), SPEC-06 sgdma_mm_rd rev 1.0, SPEC-12 (Harness guide), the J3 README/TB connections documents, and the RTL drop/version recorded in the test plan header.

1. Stimulus

Agents. CMD_AGENT is the only stimulus that triggers the DUT. DOUT_AGENT and STATUS_AGENT are reactive receivers, started first by the virtual sequence. The memory model is not driven by an agent. The test preloads it with an address-derived pattern (data = f(address)) so every byte is unique and identifiable.

Directed tests (corner cases from the spec):

  • Lengths 1, 2, 3, 4, 5, 63, 64, 65, 100, and the maximum 65535, to hit every keep_mask and burst count.
  • Starts at 0x0FFC, 0x0FF0, 0x1000, 0x0FC0 with 200 B, to hit 4 KB splits and 64 B cuts.
  • inc_addr = 0 with lengths over 64 B (FIXED bursts, same ARADDR each time, no 4 KB split).
  • Illegal commands: len_bytes = 0 (no AR, err = 1, bytes_done = 0) and an unaligned addr. I don’t have the full illegal list of the read block, so confirm it in SPEC-06.
  • Error responses: SLVERR on the first beat, a middle beat, and the last beat of a burst, and in the second burst of a multi-burst command.

Constrained-random tests:

  • Command fields: addr (aligned, biased toward 4 KB edges), len_bytes (biased toward small, boundary and large values), inc_addr, desc_id.
  • Sequences of 10 to 100 commands with different lengths and modes, sent back to back.

Timing knobs (set per test through config objects, selectable from the virtual sequence):

2. Checking

Reference model (inside the scoreboard). It is built from three inputs:

InputFromUsed to predict
Command (addr, len, inc_addr, desc_id)CMD monitorThe burst plan (min of remaining bytes, 64 B, bytes to the 4 KB boundary), the number of beats, the final keep, the expected status
Memory contentsMemory model backdoor (preloaded pattern)The expected data bytes, independent of the DUT
Observed AR/R trafficPASSIVE monitorActual bursts, and which beat carries the first RRESP error

The expected data comes from the memory contents, not from the observed R beats. That keeps the check independent. The R beats are used only to locate the first error.

Scoreboard comparisons (transaction level, never cycle counts):

  • AR sequence: ARADDR, ARLEN, ARBURST equal the predicted bursts. Total bytes equal len_bytes.
  • dout beats: data, keep and order equal the prediction. last is on the final beat only (or the last beat of the erroring burst after an error).
  • Status: desc_id equals the command’s, eop_seen = 0, err as expected, bytes_done = len_bytes (normal), bytes before the first error beat (failing), or 0 (illegal).
  • Exactly one status per command (IF-CMD-002).

3. Reset strategy, error injection and debug

Reset. The testbench applies the asynchronous active-low rst_n. All drivers hold valid = 0 during reset (IF-RST-001). Every test starts with a reset and a check that the DUT comes up idle with cmd_ready = 1. A dedicated test asserts reset in the middle of a command (during AR, mid-burst, and with the status pending). After it, the scoreboard flushes its queues, drivers and monitors abort their current items, and a normal command must then complete correctly.

Error injection.

  • Response errors: the memory model returns SLVERR for chosen addresses or beats. The scoreboard predicts err and bytes_done from the position of the first error.
  • Illegal commands: sent by CMD_AGENT with len_bytes = 0 or unaligned addresses.
  • Protocol stress: the testbench never violates the DUT’s input rules except in a deliberate negative test, so a failing assertion always points at the DUT.
